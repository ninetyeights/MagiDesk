# 签名更新发布指南（SEC-07）

已接入 ECDSA P-256 / SHA-256 签名验证，无新增第三方依赖。客户端只信任编译时嵌入的公钥，不信任 Release、磁盘配置或安装助手命令行提供的公钥/摘要。首版生产公钥已由发布者生成并加入仓库；私钥保持在本机仓库外，不要把密码发到聊天中。

## 一次性初始化

在仓库根目录的本地 PowerShell 终端执行：

```powershell
powershell -NoProfile -File scripts/Update-Signing.ps1 init
```

工具提示输入并确认至少 12 字符的密码，不回显；请使用密码管理器生成的长随机密码。密码不接受命令行参数、环境变量或重定向输入。

- 默认私钥位置：`%LOCALAPPDATA%\MagiDesk Signing\release.key`，在仓库之外。可用 `-PrivateKeyPath` 指定其他私有目录。
- 私钥为密码加密的 PKCS#8 DER，PBES2 / AES-256-CBC / PBKDF2-HMAC-SHA256，600,000 次迭代；加密参数由 .NET 生成，不自造算法。
- 公钥写入 `MagiDesk/Features/Updates/UpdateKeys.json`。公钥编号是公钥 SPKI 字节的 SHA-256；此 JSON 可以提交，私钥绝不能提交或上传。
- `init` 使用 CreateNew，不覆盖已有私钥。公钥写回失败时可用 `trust` 命令从原私钥重新导出公钥，无需重新生成。
- 立即备份加密私钥到离线介质，密码另行保管；避免放入自动同步/共享目录。建议在独立、可信发布电脑上签名。

初始化完成后必须重新构建应用，公钥才会嵌入。空公钥配置可开发构建，但在线更新拒绝工作，正式打包脚本会拒绝产出发行包。没有示例私钥或测试公钥作为默认信任锚。

## 每次发布

1. 更新应用版本，执行原来的 `scripts/Publish-Release.ps1 -Installer`。安全检查及公钥检查必须通过。
2. 如需双架构，分别生成 x64 和 ARM64 安装包；两个安装包必须使用同一应用版本和预期公钥配置。不要给旧的无公钥程序签发“带签名升级”后误以为旧客户端会验证。
3. 执行签名命令（以下文件名仅为示例，请替换为实际输出）：

```powershell
./scripts/Update-Signing.ps1 sign -Version '0.1.0-beta.2' `
  -OutputDirectory '.\publish\signed-beta.2' `
  -InstallerPath '.\publish\MagiDesk-0.1.0-beta.2-win-x64-Setup-20261003-120000.exe'
```

双架构在 PowerShell 中给 `-InstallerPath` 传入两个路径的数组，一起生成一个清单。重新签名使用新输出目录，不覆盖已有清单/签名对。

4. 在本机输入私钥密码，核对工具显示的版本、架构、大小和 SHA-256，再输入 `SIGN`。工具先用仓库公钥配置验证自己的签名，然后写出两个文件。
5. 创建 `v版本号` 的 GitHub Release，将以下文件一起上传：
   - 实际参与签名的安装 EXE（一个或两个）。
   - `update-manifest.json`。
   - `update-manifest.sig`（64 字节二进制，非 Base64/文本）。
6. 签名后不要格式化、增删字段或改变清单换行。`.exe.sha256` 可继续上传供人工校验，但客户端不会使用它作为信任依据。
7. 用已内置公钥的较旧版本进行真实升级验收；签名工具、客户端和安装助手均不会帮你上传文件。

原 Release 的名称、说明只用于发现与展示，显示为普通文本；真正用于安装的版本、渠道、架构、文件名、URL、大小与摘要由签名清单约束。

## 清单协议与失败处理

清单包含 `schemaVersion: 1`、`keyId`、`version`、`channel`（stable/preview）以及 `packages`。每个包包含 runtime、name、download、size、sha256；每种架构最多一项。

签名对象是 UTF-8 清单原始字节，ECDSA P-256 + SHA-256，使用 IEEE P1363 固定格式 r || s。验证时限制清单 64 KiB、签名 64 字节、JSON 深度 8，并拒绝重复字段、未知协议版本、不支持的字段/架构、跨仓库下载地址、路径穿越文件名及超过 512 MiB 的安装包。

客户端先验证签名，后解析可信安装信息；只允许高于当前版本的更新，正式版不接收 preview。缺少签名、签名错误、未知密钥、架构/版本不符会停止更新，不回退到无签名或仅 SHA-256 校验。

缓存同时保存原始清单及签名。安装助手只接收父进程 PID 和安装文件路径，等待退出后独立读取、验证内置公钥签名，检查当前版本/架构/文件名/大小/SHA-256，保持文件只读锁直到启动安装器。网络请求逐跳限制 HTTPS 官方主机。

网络/仓库攻击者仍可删包、隐藏更新或重放一个高于当前版本的旧签名版本，导致更新被冻结或不够新；当前方案防止未签名代码与安装版本降级，不声称提供完整 TUF 式新鲜度保护。签名者不得重发同一版本的不同内容，应增加版本号。

## 密钥轮换和事故

- 正常轮换：使用 `init -PrivateKeyPath <新的路径>` 生成第二把密钥，工具保留旧公钥。先用旧私钥签发同时信任新旧公钥的过渡客户端，再切换新私钥。**当前更新选择器不自动走多跳升级**：未安装过渡版本的老用户需手动安装过渡/新版；不要宣称所有老用户会自动轮换成功。
- 私钥丢失：用离线备份恢复，使用 `trust` 校验并重建公钥配置。没有备份时无法继续为老客户端签名，需要用户通过独立可信渠道重新安装。
- 私钥泄露：停止使用并发布安全通知，通过独立可信渠道分发移除旧公钥的新版。当前没有在线吊销服务，不能用已泄露的私钥证明后续密钥可信。
- 仓库代码也可能被篡改：签名前必须审核源码和实际包。私钥与发布令牌不要放在同一个 CI 信任域。

签名清单不等于 Windows Authenticode；安装程序显示的发布者身份及 SmartScreen 信誉仍需另行处理。

## 验证边界

本轮使用运行时临时生成的测试密钥，不保存生产私钥。已覆盖签名篡改、清单改动/重新格式化、未知签名者、重复字段、超限清单、旧版本/错误渠道/架构、损坏安装包和安装助手复验；检查失败不会请求安装 EXE。真实密码交互、正式密钥备份、真实 GitHub 更新和安装器运行需发布者本机完成验收。

## GitHub Actions + tag 发布

推送与项目版本一致的标签（首版 `v0.1.0-beta.1`）触发 `.github/workflows/release.yml`。两个 Windows 构建任务分别执行安全扫描、测试并生成 x64 / ARM64 安装包和 ZIP；全部通过后创建草稿 Release。使用 runner 自带的 Inno Setup，具体 runner 工具版本记录在 Actions 初始化日志中。工作流不会覆盖已有 Release，也不持有私钥。

从草稿下载两个安装 EXE，在本地用上面的 sign 命令一起签名。将生成的清单和签名放到两个安装包旁边，执行：

```powershell
./scripts/Update-Signing.ps1 verify -Version '0.1.0-beta.1' -OutputDirectory '<安装包与签名所在目录>'
```

verify 不读取私钥，会校验真实签名、版本、每个安装包大小及 SHA-256。通过后上传两个签名文件，核对远端文件再发布草稿。密码始终只在本机交互终端输入。
